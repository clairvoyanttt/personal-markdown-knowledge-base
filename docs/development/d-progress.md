## 2. 三包独立工作的交付边界

### D01：三个应用服务、接口草案与替身测试

- API07 导出：验证请求和当前集合，拒绝无保存版；处理未保存选择，仅消费冻结保存版；
  串联默认/自选命名、引用转换和文件发布，返回准确的路径、版本及结果。
- API08 备份：实现现有 `BackupService` 的 D 侧编排，核对全部草稿状态和 `NO_UNSAVED` 声明；
  绑定来源集合、实际快照捕获事实和清单，再执行打包发布；不读取草稿冒充保存版。
- API09 恢复：编排归档检查、候选准备、C 校验和受控初始化、发布及返回位置/数量；
  不自动打开、不改原集合或备份；可以在没有活动集合时恢复。
- 三者共同覆盖：输入类型和 Context/代次保护、旧结果不污染当前界面、后台执行边界、
  取消、普通失败、部分效果及未知结果、公开错误映射、自有资源收尾。
  不自动保存、不把文件发布未知交给 SAVE 核实，不把迟到取消当成回滚。
- 已用明确的内部窄端口和测试替身验证 D 的规则，不伪称已接入真实数据库或界面。
  API07/09 请求/回复、快照/解析/初始化端口、正式 manifest 字段与版本均须列出调用样例和待确认点。

### D02：安全恢复文件流水线

- 在同一次受控输入读取中验证归档并提取指定快照到独占工作区，绑定实际摘要/大小；
  防止“检查后重新打开同一路径，却处理了另一份备份”。不使用无约束 `extractall`。
- 处理空目标要求、目标变化/并发抢占、不可写、短写、资源预算、取消与清理失败；
  原集合、原备份和目标已有内容均不得被误改。
- 只清理可以正面确认归属的未发布产物。候选不是有效恢复集合，也不能凭清单一致就宣布恢复成功。
- 通过窄端口交给 C 校验/初始化，再与 A 复用正式集合发布边界；
  不绕开 C 直接修改用户数据库，不复制第三套集合发布逻辑。

交付证据：[候选流水线](../../src/pmkb/application/backup_restore/candidate.py)及
[候选故障测试](../../tests/test_d_restore_candidate.py)。

仅按自有目录/文件身份清理。原有只读 ZIP 检查器没有被悄悄改成提取器。
C 仍须在自己的受控句柄边界核对输入，不把候选报告当作后续 unchecked reopen 的授权。
